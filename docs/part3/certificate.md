# 国密数字证书与 PKI 体系

国密证书是国密信任体系的外壳：算法是 SM2，但**证书的格式、签发流程、密钥托管制度**才是它与国际 PKI 的真正区别。本章依据 GM/T 0015-2012《基于 SM2 密码算法的数字证书格式规范》及配套密管规范展开。

## 1. 国密 PKI 的角色架构

```text
             ┌──────────────────────────────────────────────┐
             │                  CA（证书认证机构）             │
             │  签发证书、维护 CRL/OCSP、根证书与证书链          │
             └───────┬───────────────────────────┬──────────┘
                     │ 签名密钥对（用户本地生成）      │ 加密密钥对（KMC 生成）
             ┌───────┴───────┐             ┌───────┴──────────┐
             │  RA（注册机构） │             │  KMC（密钥管理中心）│
             │  实体身份审核   │             │  加密私钥生成/托管/  │
             │              │             │  恢复、密钥历史管理  │
             └───────────────┘             └──────────────────┘
                     ▲                              ▲
                     │ 申请（CSR + 身份材料）          │ 加密私钥安全下发
                     └────────── 用户/服务器 ─────────┘
```

与国际 PKI 最大的不同是 **KMC 的存在**：CA 不掌握签名私钥（与国外一致），但用户的**加密私钥由 KMC 生成并在托管体系内保存**（可依授权恢复），这是双证书制度的信任基石，也是 TLCP 加密流量的"制度性后门"（见 TLCP 章安全分析）。

## 2. 双证书的生成与签发流程

```text
签名证书（签名密钥对自主可控）：
  1. 用户在本地（密码设备内）生成 SM2 签名密钥对
  2. 提交 CSR（PKCS#10，公钥 + 身份 + 证明）
  3. RA 审核 → CA 用 SM2withSM3 签发证书
  4. 私钥全程不离开用户设备

加密证书（加密密钥对受托管理）：
  1. KMC 生成 SM2 加密密钥对
  2. CA 对加密公钥签发加密证书
  3. KMC 将加密私钥经安全通道（或离线介质）下发用户，
     同时入库托管（支持依司法/行政授权恢复）
```

两张证书主题（Subject）相同、序列号不同、密钥用途互补。证书到期换发时，**签名密钥对应重新生成**，而加密私钥按密管策略可延续（保证历史密文可解）。

## 3. 证书格式

国密证书基于 **X.509 v3**（GM/T 0015 对格式做了国密化约定），一张实测生成的 SM2 证书（OpenSSL 3.x，输出节选）：

```text
Certificate:
    Data:
        Version: 3 (0x2)
        Signature Algorithm: SM2-with-SM3          ← 国密签名算法
        Issuer: C = CN, O = Demo, CN = www.example.sm
        Subject: C = CN, O = Demo, CN = www.example.sm
        Subject Public Key Info:
            Public Key Algorithm: id-ecPublicKey    ← 仍是标准 EC 公钥算法
            Public-Key: (256 bit)
            pub: 04:e5:ec:99:...:2e                 ← 未压缩 SM2 公钥点
            ASN1 OID: SM2                            ← 曲线标识
        X509v3 extensions:
            X509v3 Basic Constraints: critical ...
        Signature Algorithm: SM2-with-SM3
        Signature Value: 30:45:02:21:00:e8:...      ← DER 序列 (r, s)
```

格式要点：

- **公钥算法 OID**：`id-ecPublicKey (1.2.840.10045.2.1)` + 曲线 OID `SM2 (1.2.156.10197.1.301)`——即"标准 EC 框架装国密曲线"，与国际 ECDSA 证书结构同构；
- **签名算法 OID**：`SM2-with-SM3 = 1.2.156.10197.1.501`；
- **密钥用途**：签名证书 `digitalSignature + nonRepudiation`；加密证书 `keyEncipherment + dataEncipherment`（TLCP 会检查该扩展以区分证书职能）；
- 序列化兼容性：标准 X.509 工具（OpenSSL 1.1.1+、多数 ASN.1 库）可直接解析国密证书，差别只在算法 OID 识别与验签实现。

## 4. 常用 OID 速查（中国密码标准弧 1.2.156.10197）

| OID | 含义 |
| --- | --- |
| 1.2.156.10197.1.301 | SM2 椭圆曲线（证书中的曲线标识）；子树 301.1/.2/.3 为签名/密钥交换/加密 |
| 1.2.156.10197.1.401 | SM3 杂凑（401.2 为 HMAC-SM3） |
| 1.2.156.10197.1.501 | SM2WithSM3（证书 `SignatureAlgorithm`；502~50x 为 SM2 搭配 SHA 系变体） |
| 1.2.156.10197.1.104.2 | SM4-CBC（SM4 模式族：104.1 ECB、104.7 CTR、104.8 GCM、104.9 CCM…） |

> 经验：**跨库互操作优先显式传算法，别赌 OID**。SM4 的 OID 按 GM/T 0006 以工作模式区分（104.x 族），忘记模式后缀是常见错误。

## 5. 实战：生成国密证书

命令行生成（OpenSSL 1.1.1+/3.x 原生支持 SM2 曲线与 SM3 摘要签名；Tongsuo 另支持 `-sm2` 快捷参数）：

```bash
# 签名密钥对（应生成于密码设备内，此处演示软件密钥）
openssl ecparam -name SM2 -genkey -noout -out sign.key

# 自签测试证书（生产环境应向持牌 CA 提交 CSR）
openssl req -x509 -new -key sign.key -SM3 -days 365 \
  -subj "/C=CN/O=Demo/CN=www.example.sm" -out sign.crt

# 查看/校验
openssl x509 -in sign.crt -noout -text
openssl verify -CAfile sign.crt sign.crt
```

注意：OpenSSL 的 `-SM3` 参数使 req 采用 SM2withSM3 签名；签发双证书时把上面的流程对"加密密钥对"再走一遍（并向 CA/KMC 申请正式加密证书）。CSR（PKCS#10）结构本身无需国密化，只是签名算法换为国密。（本节命令已在 OpenSSL 3.0.x 实测通过：证书签名算法显示 `SM2-with-SM3`、曲线 OID `SM2`、自签校验 OK。）

## 6. 信任链与证书状态服务

- **证书链**：与国际 PKI 同构——根 CA（自签）→ 中间 CA → 实体证书；验证时逐级 SM2 验签到信任锚。国内大环境的信任锚通常是**预置在操作系统/浏览器/网关里的国密根证书**（如 CFCA 及各行业根）；
- **CRL/OCSP**：格式遵循国际标准（CRL 同样用 SM2withSM3 签名）；国密 OCSP 响应也用 SM2 签名。网关类产品普遍内置 CRL 自动下载。运维实践：国密生态里 **CRL 仍是主流状态服务**（定时下载、全量校验），OCSP 服务与客户端 stapling 支持的覆盖面不及国际生态——高并发网关若依赖证书状态做准入，优先设计"本地 CRL 缓存 + 定时拉取"而非在线 OCSP 查询，并注意两张证书（签名/加密）可能进入不同的吊销通道；
- **证书透明（CT）与自动化**：国际生态的 CT 日志、ACME 自动签发在国密体系尚无对应物——国密证书的申请/换发走 CA 门户或 RA 流程，**到期换证是人工运维动作**，批量网关的证书到期监控（分别盯两张证书的有效期，见密钥管理章）必须自建告警；
- **国密 CA 生态**：CFCA（金融）、各省级/行业 CA（政务）等持牌机构构成签发体系；根信任的分发仍在建设期——不同客户端预置的国密根集合并不一致，B 端集成时经常需要手工导入根证书。

## 7. 双栈并存（国密 + 国际）部署模式

真实系统几乎都要同时服务国密客户端与国际客户端，通用模式：

```text
                      ┌─ SNI/套件探测 ─┐
客户端 ──► 边缘分发层 ─┤                ├──► 国密虚拟主机（TLCP 双证书 / RFC 8998）
                      └────────────────┘──► 国际虚拟主机（TLS 1.3 RSA/ECDSA）
```

- 分发依据：客户端 ClientHello 里的套件（是否含 E0xx / 00C6）或 SNI 域名；
- 证书配套：同一域名准备"国密双证书 + 国际证书"两套材料；
- 风险点：跨协议填充攻击类研究（如跨 TLS 版本的降级）提示双栈网关要严格隔离两个协议栈的实现状态，避免共享会话缓存。

## 8. 证书生命周期管理要点

| 阶段 | 国密特有动作 |
| --- | --- |
| 申请 | 签名/加密两套流程并行；加密证书必须走 KMC 通道 |
| 部署 | 双证书成对部署、顺序正确（签名在前）；私钥载体优先硬件（UKey/密码卡） |
| 运行 | 监控证书有效期（两张证书到期日可能不同步！） |
| 换发 | 签名对换新、加密私钥按密管策略延续/重托管 |
| 撤销 | 双证书分别进入 CRL；加密证书撤销后需通知 KMC 停止派发相关密钥服务 |
| 归档 | 托管加密私钥的历史归档决定历史密文的长期可解性（司法调证依赖） |
