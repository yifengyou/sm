# 可信计算与 TCM

可信计算解决的是"**信任的起点**"问题：密码算法保护数据，但谁来保证运行密码算法的平台本身没被动过手脚？国际答案是 TPM（TCG 体系），国密的答案是 **TCM（可信密码模块）体系**，以及演进到"主动度量"的**可信计算 3.0**。

## 1. 基本思想：从可信根开始的度量链

```text
加电
 └─► 可信根（TCM/TPCM 芯片，硬件不可篡改）
      └─► 度量 BIOS/固件 ──► 度量引导程序 ──► 度量内核 ──► 度量应用/配置
           每一步把"下一步的完整性摘要"写入芯片内的平台配置寄存器（PCR 类寄存器）
           并与预期值比对 —— 摘要算法用 SM3，比对与签名用 SM2
```

核心性质：度量值只能**扩展写入**（新值 = SM3(旧值 ‖ 新度量)），无法回滚伪造——链条上任何一环被篡改，远端验证者都能通过挑战-应答（对 PCR 值的 SM2 签名）发现。

## 2. TCM：国密的可信根

TCM 芯片的功能构成：

| 部件 | 国密实现 |
| --- | --- |
| 算法引擎 | SM2 签名/解密、SM3 摘要、SM4 对称加密（一个芯片就是最小国密子系统） |
| 平台配置寄存器 | 存放度量链值的寄存器组，只支持扩展 |
| 密钥树 | 平台身份密钥（背书密钥，出厂唯一）→ 存储密钥（层级包裹）→ 签名/加密密钥（可迁移/不可迁移） |
| 授权与会话 | 密钥使用授权（口令/HMAC 会话），防重放计数器 |
| 封密存储 | 密文与 PCR 值绑定：平台状态不对则密钥解不开（"只有健康状态才能拿到数据密钥"） |

标准载体：**GB/T 29829-2015《信息安全技术 可信计算密码支撑平台功能与接口规范》**规定 TCM 及其支撑软件（TSM 服务模块，对应 TCG 的 TSS）的功能与 API；行标侧另有 GM/T 0011-2023《可信密码支撑平台功能与接口规范》（替代 GM/T 0011-2012）与 GM/T 0012-2020（TCM 接口规范）构成现行体系；早期配套的接口符合性测试规范（GM/T 0013-2012 系列）已被新版替代（以密标委现行目录为准）。

## 3. 可信计算 3.0：从被动到主动

中国体系（可信计算 3.0，沈昌祥院士推动）与国际 TCG 体系的关键分野：

| 维度 | TPM（TCG，被动度量） | TPCM（中国，主动度量） |
| --- | --- | --- |
| 芯片角色 | 主 CPU 启动后被动的存储/签名协助者 | **先于主 CPU 加电**，作为"双内核"之一主动控制启动流 |
| 度量时机 | 静态度量（启动链条） | 静态 + **动态度量**（运行时按策略拦截/度量） |
| 防护哲学 | 记录+证明，供远端裁决 | 主动免疫：不满足策略直接阻断执行 |
| 计算模式 | 外挂安全芯片 | 计算与安全并行的体系化改造 |

对应用者的意义：国产化整机（飞腾/龙芯/鲲鹏 + 国产 OS）在政务、电力、金融的落地项目中，"TPCM + 国产 OS 可信基（TBase 类软件层）"已成标配卖点；开发者在这些平台上可能直接面对"程序需通过度量白名单才能跑"的运行环境——应用要把"自身度量值/签名"纳入交付物。

## 4. 远程证明与 TEE：两块常被混淆的邻近概念

**远程证明（remote attestation）**——第 1 节挑战-应答的展开：验证方想知道"远端平台当前运行的是不是预期软件栈"。流程骨架：

```text
验证方 ── 随机挑战 nonce ──► 被证方
被证方：TCM 用平台身份密钥（AIK 类）对 { nonce ‖ PCR 值快照 ‖ 度量日志 } 做 SM2 签名 ──► 验证方
验证方：核验签名（防重放靠 nonce）→ 拿 PCR 值与"已知良好基线"比对 →
        重放度量日志逐项核对每一环摘要 → 裁决是否信任该平台
```

工程要点：证明报告的**新鲜性**完全依赖 nonce（防重放）；**基线库**是运营负担（每次合法升级要同步更新预期 PCR 值，与第 5 节"度量值漂移"是同一个问题）；证明只能说明"启动时 + 度量点上的状态"，与可信计算 3.0 的动态度量配合才能覆盖运行时。

**TEE（可信执行环境）与 TCM 的关系**——移动端密钥保护的承重概念（协同签名章的"客户端分量受 TEE 保护"即指此）：

| | TCM/TPCM（可信根） | TEE（TrustZone/安全 enclave） |
| --- | --- | --- |
| 解决的问题 | 平台完整性度量与证明 | **一段代码/数据的隔离执行**（普通 OS 也读不到） |
| 形态 | 独立安全芯片/先启核 | 主 SoC 内的隔离世界（ARM TrustZone、x86 SGX 类） |
| 密码角色 | SM3 度量 + SM2 证明 + 封密存储 | 隔离区内运行 SM2/SM4 逻辑、密钥只在区内明文存在 |
| 典型组合 | 服务器/整机可信基线 | 手机 App 的密钥分量、DRM、指纹比对 |

两者互补而非替代：TEE 保障"密钥运算过程隔离"，TCM 保障"平台没被篡改"；移动端国密方案（协同签名、SIM-Key）的客户端分量普遍落在 TEE 内，国密侧的标准载体是 **GM/T 0146-2025《可信执行环境密码安全管理框架与接口》**（TEE 内密码模块的管理与接口要求）。注意 TEE 的信任根仍是芯片厂商（TrustZone 的安全世界由 SoC 信任链锚定），与 TCM 的"国产可信根"是不同的信任模型，密评材料里要分别说明。

## 5. 与等保、密评的交点

- **等保 2.0** 在各级新增"可信验证"控制点：一级要求"验证设备引导过程"，三级要求"基于可信根对计算环境（程序动态执行）进行验证"——落地即 TCM/TPCM 体系；
- **密评视角**：可信计算平台本身就是密码应用的集大成者（度量摘要=SM3、身份=SM2、封存=SM4），采购可信计算产品同样核验商用密码产品认证证书；
- 组合拳形态：整机的可信根 + 网络的 TLCP + 应用的数字信封/签名，构成从硬件到应用的三层国密防线——这也是"等保+密评"双评协同的典型架构样板。

## 6. 实务提示

1. 存量 TPM（国际芯片）平台做国密改造时，可用"TPM 承载国密密钥的混合方案"过渡，但密评会追问国密算法覆盖率；
2. 动态度量策略要灰度：先只告警不阻断，观察误报（应用自更新导致度量值漂移是最常见的"事故"——**软件升级流程必须同步更新度量预期值**）；
3. 虚拟化/容器环境：度量粒度从"可执行文件"扩展到镜像摘要与配置哈希，TCM 的封密存储同样适用于云主机的磁盘密钥。
