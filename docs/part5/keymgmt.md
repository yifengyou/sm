# 密钥管理体系

密钥管理是密码工程的"操作系统"：算法是函数，密钥才是资产。国密语境下它还有制度层含义——GB/T 39786 的管理要求、KMC 托管、密评台账检查都围绕密钥生命周期展开。

## 1. 密钥生命周期与责任矩阵

```text
生成 ─► 分发 ─► 存储 ─► 使用 ─► 更新/轮换 ─► 归档 ─► 销毁
 │       │        │        │        │           │        │
设备内   安全信道   加密托管   最小暴露   周期策略   司法/审计   可证明
生成     或离线    或硬件     原则      与触发式   保留期     抹除
```

| 阶段 | 国密语境的关键要求 |
| --- | --- |
| 生成 | 合规随机源（见随机数章）；密钥对在密码设备内生成，私钥不出设备 |
| 分发 | 私钥经安全信道/离线仪式下发；对称密钥经密钥协商或信封加密分发 |
| 存储 | 软密钥必须加密存储（见下节保护结构）；硬密钥只在设备内，外部仅存句柄 |
| 使用 | 用途单一（签名/加密分离——双证书的制度化体现）；访问审计 |
| 轮换 | 会话密钥每会话；DEK 定期/按量；KEK 年度级；根密钥极少轮换（仪式级） |
| 归档 | 加密私钥与历史数据的解密能力绑定（KMC 托管的核心动机） |
| 销毁 | 存储介质级抹除；设备内密钥销毁留痕 |

## 2. 三层密钥架构与信封加密

工业界的标准实践在国密语境的对应形态：

```text
根密钥/主密钥（RMK）      生成并永驻 HSM/密码机内，物理保护
   │  用于包裹
   ▼
密钥加密密钥（KEK）       加密存储的"密钥的密钥"，HSM 内解包
   │  用于包裹
   ▼
数据密钥（DEK）/ 会话密钥  明文只在内存/一次运算中出现，用后即弃
```

好处：换 DEK 不动 KEK，换 KEK 不动 RMK；KMS/密码机集群只需要保护最顶层。国密材料映射：DEK=SM4 密钥，包裹=SM4-GCM/CBC 信封，跨主体分发=SM2 数字信封（见消息语法章）。

## 3. 密钥派生（KDF）选型

国密体系里"从秘密派生密钥"的函数不止一个，工程里经常拿错（跨实现联调的高发坑）。统一速查：

| KDF | 构造 | 出处 | 典型用途 |
| --- | --- | --- | --- |
| **国密 KDF**（SM3 计数器模式） | SM3(Z‖ct) 级联截断 | GB/T 32918.1 / 35276 | SM2/SM9 的会话密钥派生、GB/T 35276 私钥口令封装、标准体系内一切 KDF 槽位 |
| HMAC-SM3 | RFC 2104 套 SM3 | OID 1.2.156.10197.1.401.2 | 报文 MAC、TLCP 记录层与 PRF 基础 |
| **HKDF-SM3** | HKDF-Extract/Expand | RFC 8998（TLS 1.3 密钥调度） | TLS 1.3 国密套件、工程自建的分层密钥 |
| PBKDF2-HMAC-SM3 | RFC 8018 | 工程实践（无强制国标） | 口令→密钥（自建私钥文件加密等） |
| KBKDF | SP 800-108 计数器模式，HMAC-SM3 作 PRF | 工程实践 | 从主密钥派生用途隔离的子密钥 |

要点：

- **KDF 输入必须带"用途/上下文"标签**（label、ID、算法标识）：没有标签的派生会让同一秘密长出可跨用途流动的密钥——相关密钥攻击的经典入口；
- **TLCP 与 TLS 1.3 国密套件的密钥调度不通用**：TLCP 走 TLS 1.2 式 PRF（HMAC-SM3），RFC 8998 走 HKDF-SM3——从 TLCP 移植代码时这是隐性差异（见 TLCP 章）；
- **口令派生与口令存储是两个问题**：存口令摘要优先 Argon2/bcrypt（慢哈希）；需要从口令恢复出密钥的场景用 PBKDF2-HMAC-SM3，迭代次数按当前算力调优（建议不低于 10⁵~10⁶ 量级）、盐每文件唯一。OpenSSL 3.x 的 `enc -pbkdf2 -md sm3` 即此组合（本手册实测可用）；
- **注意 GB/T 35276 的口令封装内部走国密 KDF 而非 PBKDF2**——两者结构不同，跨库互导"加密私钥文件"时先对齐封装结构（见第 9 节互操作坑清单）。

## 4. 密钥的物理形态

| 形态 | 载体 | 典型接口 | 适用 |
| --- | --- | --- | --- |
| 硬密钥 | 密码卡/密码机（SDF 内部密钥） | GM/T 0018 | 服务器侧签名/解密 |
| 硬密钥 | USB-Key / SIM-Key | GM/T 0016（SKF） | 个人/柜面 |
| 受保护软密钥 | PEM/PKCS#8，对称加密封装 | 文件+口令/PIN | 移动端过渡、测试 |
| 协同密钥 | 客户端分量 + 服务端分量 | 私有协议/协同签名规范 | 手机 App（见第 6 节） |

**SM2 私钥的保护结构**：GB/T 35276-2017 定义了 SM2 私钥（对）的对称加密封装格式——用 SM4 加密私钥并附 SM3 校验，配合口令派生密钥使用；gmsm 的 `sm2_envelopedkey`、多数 SDK 的"加密私钥文件"都出自此结构。生产环境软私钥至少要达到这一档，裸 PEM 私钥在密评中直接扣分。

## 5. 国密特有：双密钥的分治管理

双证书制度（见证书与 TLCP 章）把密钥管理切成两条流水线：

| | 签名密钥对 | 加密密钥对 |
| --- | --- | --- |
| 生成方 | 用户设备内 | KMC（密管中心） |
| 托管 | **禁止托管**（可托管即可伪造签名） | 制度化托管（支持司法恢复） |
| 轮换 | 随证书换发，应换新 | 可延续（保历史密文可解） |
| 撤销后果 | 立即失效，历史签名仍有效 | 历史密文仍需可解（依赖归档） |
| 泄露后果 | 伪造签名风险 | 历史密文暴露 |

运维提示：**两张证书有效期可能不同步**——监控告警要分别盯；KMC 通道（加密私钥下发/恢复）要有完整的授权与审计流程，这本身就是密评的核查对象。

## 6. 协同签名：移动端的"密钥不落盘"

移动端私钥保护的痛点：软件私钥文件可被导出/逆向；硬件 UKey 体验差。**协同签名（两方协同 SM2 签名）**给出第三条路：

```text
 setup：d = d₁ + d₂ (mod n)
   d₁ —— 客户端分量（App 内，受白盒/TEE 保护）
   d₂ —— 服务端分量（签名服务器 HSM 内）
   完整私钥 d 任何时刻、任何一方都不存在

签名时：客户端出 d₁·G 相关的盲化交互，服务端以 d₂ 参与，
 两轮（或三轮）交互后产出一个标准的 SM2 签名 (r, s)——
 对验签方完全透明，验签流程与普通 SM2 签名一致
```

- 安全性质：单方被攻破（客户端逆向或服务器失陷）都拿不到私钥；服务端还能做**策略控制**（限次、限额、风控阻断）；
- 代价：签名变成在线协议（两方交互），离线场景不可用；实现复杂度显著高于普通签名，交互协议必须防中间人/重放（通常叠加 TLCP 通道）；
- 生态：密码厂商（三未信安、海泰方圆等）的"协同签名系统"已在证券、政务 App 中规模化落地；相关密码行业标准陆续制定（以密标委公告为准）；
- 变体：协同解密（SM2 加密的协同解封）、门限 SM2（t-of-n 分量，密标委体系内亦有研究标准化的方案）。

选型判断：高频移动端签名（转账确认、电子合同）→ 协同签名或 TEE+SE；低频/内部场景 → UKey 或加密软私钥即可。

## 7. KMC（密钥管理中心）与恢复制度

KMC 的职能清单（对应密管系列标准与产品规范）：

- 加密密钥对的生成、编号、下发（与 CA 联动签发加密证书）；
- 托管库管理：加密私钥分量入库、门限分片存储（多地分存，M-of-N 恢复）；
- 司法/行政调证流程：授权、双人复核、全程审计、只按密文粒度恢复；
- 密钥历史管理：用户多代加密私钥的档案，支持按时间点解密历史数据。

工程注意：KMC 是整个体系的价值高地，其自身安全等级要求高于业务 CA（主密钥分片、异地灾备、离线备份介质双人双锁）。对业务方而言，接 KMC 体系意味着接受"加密流量可被制度性恢复"的安全模型——金融/政务默认接受，互联网隐私场景需要明示。

## 8. 轮换策略参考表

| 密钥类型 | 建议周期 | 触发式轮换 |
| --- | --- | --- |
| 会话密钥（TLCP/应用层） | 每会话 | — |
| DEK（数据加密） | 按数据集/季度 | 泄露嫌疑即换 |
| API 签名密钥 | 季度~年度 | 人员变动、疑似泄露 |
| KEK | 年度 | HSM 更换、安全事件 |
| 根密钥/CA/KMC 主密钥 | 多年/极少 | 仪式级流程（M-of-N 分片重铸） |

## 9. 常见违规与自查

1. 私钥/密钥硬编码进代码或配置（用 git 扫描工具全量扫描历史提交）；
2. 私钥文件权限 644、随镜像打包进容器层；
3. 日志打印密钥/密文+IV 组合（日志系统成为密钥泄露面）；
4. 测试环境密钥进了生产（测试/生产密钥清单分离）；
5. 无密钥台账（密评要求：密钥清单、用途、责任人、轮换记录可追溯）；
6. "加密了但钥匙放旁边"——密文与 KEK 同库同表存储；
7. 备份介质未加密或密钥与数据同盘备份。

自查口诀：**每一把密钥都要能回答"谁生成、存哪里、谁能用、何时换、怎么销毁"五个问题**。
