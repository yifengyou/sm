# 密码服务平台与密码中台

密评整改的主流交付形态正在从"各系统各自接密码机"转向**集中式密码服务平台**（密码中台/密码云服务）：算法、密钥、审计在一个平台上统一供给，业务系统只管调接口。本章给出参考架构、接口选型、部署模式对比与密评论证边界——它是前几章（密钥管理、工程实现、密码模块）在"平台层"的汇合点。

## 1. 为什么需要平台：散装调用的痛点

```text
散装形态（改造前）                          平台形态（改造后）
  系统 A ──SDF──► 密码机 ①                  系统 A ─┐
  系统 B ──私有SDK──► 密码机 ②                       ├─► 统一密码服务 API
  系统 C ──软算法──► 应用内联                       │      │
  系统 D ──……                                系统 D ─┘      ▼
                                             ┌────────────────────┐
  四套密钥管理、四份审计、                     │ 资源调度 / 密钥托管 /  │
  每次新系统重新集成一遍                       │ 审计日志 / 监控告警   │
                                             └────────────────────┘
                                                  │ SDF
                                             密码机集群 ①②③④
```

痛点清单（每条都对应密评整改项）：密钥形态不一致（软密钥散布应用）、审计无法汇聚、产品证书与实际部署两张皮、每接一个系统重写一遍集成、性能扩容只能按系统各自加机器。平台化把这些问题收敛成**一份**基础设施问题。

## 2. 参考架构：四层

```text
┌─────────────── 应用层 ───────────────┐
│ 业务系统（Web/App/网关/工控平台…）      │
├─────────────── 接入层 ───────────────┤
│ SDK（GM/T 0019 风格）/ HTTP API（GM/T 0136）
│ 网关：鉴权、限流、租户路由               │
├─────────────── 服务层 ───────────────┤
│ 密码服务：签名/验签、加解密、信封、MAC、  │
│ 时间戳代理、证书全生命周期               │
│ 密钥服务：生成/存储/轮换/归档/销毁（三层  │
│ 密钥架构 RMK→KEK→DEK 的托管实现）       │
│ 治理：审计（SM3 链式日志）、监控、告警    │
├─────────────── 资源层 ───────────────┤
│ 密码机集群（GM/T 0030）/ 云密码机        │
│ （GM/T 0142 检测）/ 密码卡 / 签名验签    │
│ 服务器（GM/T 0029）/ 软算法池（低敏场景） │
└─────────────────────────────────────┘
```

设计纪律：**密钥明文只在资源层内部存在**（密码机内生成/使用，KEK 包裹后落库），服务层只见密文与句柄（key handle/index）——"密钥不出平台/不出设备"的边界论证就建立在这条分层上。

## 3. 接口形态选型

| 形态 | 依据/风格 | 适用 |
| --- | --- | --- |
| C/Java SDK | GM/T 0019（通用密码服务接口）函数族 | 高性能内网调用（进程内/同机房）、传统集成 |
| HTTP API | GM/T 0136-2024（密码应用 HTTP 接口规范） | 云原生/多语言环境、跨网络域、第三方接入 |
| 云 KMS 风格 | 各云厂商 API（CreateKey/Encrypt/Sign…） | 已上云系统、与云 IAM/信封加密体系衔接 |

要点：对外**收敛到一种主形态**（HTTP API 的运维成本最低），SDK 留给性能敏感路径；API 设计带算法标识与版本字段（密码敏捷性，见 PQC 章）；报文签名验签接口必须支持**带 ID 的 SM2 验签**参数（Z 值互操作坑，见 SM2 章）。

## 4. 关键能力清单

- **密钥全生命周期托管**：三层架构、按用途隔离、轮换策略表、双人双岗操作（对应密钥管理章）；
- **多算法路由**：同一接口下 SM2/SM4 与（过渡期的）RSA/AES 可配置，按租户/应用开关——密码敏捷性的平台化落点；
- **高可用**：密码机集群 + 连接池 + 多活。两个高频事故源：① 连接池打满单台密码机（SDF 会话是重资源，池大小按密码机并发会话实测设定）；② 集群间会话不共享导致验证类服务跨节点失败——幂等设计 + 无状态签名/验签路由；
- **租户隔离与权限**：应用级 API 凭据 + 密钥域隔离（租户 A 永远拿不到租户 B 的句柄）+ 最小权限（只授"用指定密钥签名"而非"读密钥"）；
- **审计**：全操作日志（谁、何时、哪个密钥、什么操作、结果），SM3 链式哈希固化——密评与司法证据双用途；
- **监控**：密码机队列深度、会话占用率、签名/验签 TPS、密钥到期/轮换事件、证书链健康（两张证书分别盯，见密钥管理章）。

## 5. 部署模式对比

| 模式 | 组成 | 适用 | 注意 |
| --- | --- | --- | --- |
| 自建平台 | 自研/商用平台软件 + 自购密码机集群 | 大型机构、行业云、监管要求资源自有 | 建设周期长；平台软件自身若为密码产品须持证 |
| 云密码服务 | 云厂商密码服务平台/云密码机（GM/T 0142 检测规范） | 中小系统、快速合规 | 责任共担边界写进合同；密评时云侧材料由云商提供（检测报告、认证证书） |
| 密码机直连 | 业务系统直接 SDF 调用 | 单一系统、无多租户需求 | 仅作为过渡形态；扩到第二个系统就该考虑平台化 |

## 6. 密评视角的论证边界

1. **平台自身的产品合规**：密码机/卡/签名验签服务器持认证证书；平台软件若实现密码功能（算法、密钥管理），同样按密码产品/模块对待（GB/T 37092 等级与部署环境匹配）；
2. **"密钥不出平台"的论证材料**：分层架构图 + 资源层密钥明文边界说明 + 密码机内生成证明（SDF 内部生成接口）+ 出边界的只有密文/句柄——这是密评现场对"应用和数据层密钥安全"的核心问答；
3. **责任共担（云模式）**：密钥管理责任在谁（云 KMS 托管 vs 客户自管 KEK）、审计谁出、测评范围切分——提前与测评机构对齐，避免现场扯皮；
4. 平台**不改变业务侧的密评责任**：应用调用是否合规（如该签名处用了哈希不落的裸 MD5 类用法）、随机数来源是否走平台合规源，仍在被测系统范围内。

## 7. 工程实践坑（按踩坑频率）

| 坑 | 现象与对策 |
| --- | --- |
| 连接池 vs 密码机会话 | 高并发下 TPS 骤降/超时：SDF 会话在密码机侧是稀缺资源，池参数按厂商并发上限实测，加会话复用与预热 |
| 密钥句柄设计缺失 | 用"密钥名+版本号"做句柄（支持轮换与回滚），不要用自增 ID（迁移痛苦）；句柄与租户绑定校验 |
| 性能预算未分层 | 签名/验签与加解密混布一套资源：公钥类操作按 ops/s、对称类按 GB/s 分别预算（实测对照表见工程章），网关类"握手密集"负载单独建模 |
| 双证书只接了一张 | 接入 TLCP 网关业务时签名/加密证书的密钥用途在平台里分开管理，防止用错（对应 TLCP 章排错第 1 名） |
| 审计日志可被管理员修改 | 日志链式哈希 + 外部锚定（时间戳/上链），管理员账号双人复核（对应电子合同章的存证模式） |

## 8. 建设路径建议

```text
阶段0 盘点：算法使用点/密钥形态/产品证书现状（密评差距分析的副产品）
阶段1 核心服务：签名验签 + 密钥托管 + 审计（先覆盖密评硬性项）
阶段2 接入改造：业务系统分批切平台 API（灰度 + 双跑对照，防签名值不一致）
阶段3 治理完善：监控告警、轮换自动化、租户隔离、多活
阶段4 敏捷化：算法可配置/版本字段/混合算法预研（PQC 预留）
```
