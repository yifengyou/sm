# 工作模式与 MAC 的国标体系

"分组密码"本身只能加密 16 字节，实际系统的加密形态（流式、认证、存储、可调）全部由**工作模式**决定。国密有自己的模式标准族，其中既有与国际对齐的部分，也有**中国独有的模式与 MAC 方案**。本章把两份关键标准讲透：**GB/T 17964-2021《信息安全技术 分组密码算法的工作模式》**与 **GB/T 15852.1-2020《信息安全技术 消息鉴别码 第1部分：采用分组密码的机制》**。

## 1. GB/T 17964-2021：分组密码工作模式

标准沿革：GB/T 17964-2008 → 2021 修订版（吸收国际新成果并新增中国特色模式）。覆盖的模式：

| 模式 | 性质 | 国际对应 | 说明 |
| --- | --- | --- | --- |
| ECB | 分组独立 | SP 800-38A | 仅限单分组（密钥包裹），禁止常规数据 |
| CBC / CFB / OFB / CTR | 经典流/块 | SP 800-38A | CTR 是并行与随机访问的基础 |
| CCM | AEAD | SP 800-38C / RFC 3610 | 受限硬件友好 |
| GCM | AEAD | SP 800-38D | 高性能首选，nonce 纪律见 SM4 章 |
| XTS | 可调（tweakable）存储加密 | SP 800-38E | 磁盘/数据库扇区加密；**注意 GB/T 17964 与 NIST 的 XTS 存在参数口径差异**（gmsm 为此实现了双口径），跨库对接存储加密时先对齐口径 |
| **HCTR** | **宽块可调加密** | 独立设计（HCTR 系） | 2021 版新增，见下节 |
| BC | 块链 | 遗留模式 | 2008 版遗留，兼容存量 |
| OFBNLF | 带非线性函数的输出反馈 | 遗留模式 | 2008 版遗留，新系统不用 |

与 NIST 体系的差异一目了然：**多了 HCTR/BC/OFBNLF，少了 XEX 的显式定义（XTS 已覆盖其主流用法）**。OpenSSL 3.2+ 与 gmsm 等实现已提供国密 SM4 的全模式族（gmsm 甚至实现了 GCM-SIV、XTS 的 GB/T 17964 与 NIST 双口径）。

### 1.1 HCTR：国密的宽块加密模式

XTS 解决"扇区加密"，但它只保证**分组级**伪随机（改一个明文块只影响对应密文块）。HCTR 面向更强的需求——**宽块（wide-block）可调加密**，目标是 SPRP（强伪随机置换）：

```text
概念模型（以一个"宽块"= 多个分组为例）：
  明文宽块 ──► 拆为 中间块 + 其余块
  其余块经 多项式哈希（类 GHASH 的泛哈希）汇聚
  中间块走 CTR 流加密，其输出再反向哈希回其余块
  ⟹ 密文的任意比特依赖于明文宽块的全部比特
```

价值：任意 1 比特明文变化使整个宽块密文"雪崩"，攻击者无法做细粒度的密文 manipulation——数据库整行加密、容器镜像块加密等**防篡改要求高于保密要求**的场景是其靶心。代价：无认证标签（SPRP ≠ AEAD），吞吐低于 GCM。

学术背景（选型者应知的"为什么晚出现"）：HCTR 构造源自 2005 年的学术论文（Wang–Feng–Wang，WFW05），但**原论文的规范描述存在 bug，其后 Chakraborty–Nandi（CN08）的安全证明也发现有误**（声称的安全界不成立）——GB/T 17964-2021 采纳的是修正后的定义，这也是它直到 2021 版才进国标的原因。工程结论：实现 HCTR 必须以**标准文本**为准（勿按论文手搓），或直接用 gmsm 等已实现 GB/T 17964 口径的库（gmsm 当前未对 HCTR 做汇编优化，性能预算按 GCM 的折扣预留）。

### 1.2 填充方法（GB/T 17964-2021 附录 C）

| 方法 | 等价国际 | 形态 |
| --- | --- | --- |
| 填充方法 1 | PKCS#7 | 补 n 字节、每字节值为 n |
| 填充方法 2 | ISO/IEC 9797-1 Method 2 | 首字节 0x80 + 零填充 |
| 填充方法 3 | ISO/IEC 9797-1 Method 3 | 长度显式编码 |

工程红线：**去填充必须常数时间**（先校验再输出，不因校验失败提前返回）——CBC/ECB 系的填充预言攻击全靠"失败得快慢"。gmsm 等实现提供 `ConstantTimeUnpad()` 专用接口即为此。

## 2. GB/T 15852.1-2020：分组密码 MAC 的八种机制

消息认证码在国标中自成体系（ISO/IEC 9797-1 的中国对应）：

| 方案 | 名称 | 结构要点 |
| --- | --- | --- |
| 1 | **CBC-MAC** | 经典 CBC 取最后一块；固定长度才安全 |
| 2 | **EMAC** | 双密钥 CBC-MAC 终结加密（可变长度安全） |
| 3 | **ANSI Retail MAC** | 三段双密钥（金融零售场景传统） |
| 4 | MAC-DES | 历史 DES 形态（兼容遗留） |
| 5 | **CMAC** | OMAC/CMAC，单密钥、可变长（RFC 4493 同构，NIST SP 800-38B） |
| 6 | LMAC | 轻量变体 |
| 7 | TR-CBC-MAC | 单密钥 Retail 变体 |
| 8 | CBCR-MAC | CBC-MAC 的可变长修正 |

**工程默认选 CMAC-SM4**（方案 5）：单密钥、长度灵活、实现成熟、与国际 RFC 4493/SP 800-38B 同构便于迁移。

### 2.1 CMAC-SM4 子密钥派生（RFC 4493 同构）

```text
L    = SM4_Encrypt(K, 0^128)          # 加密全零块
K1   = L << 1  （若 L 最高位为 1，再异或 0x87）
K2   = K1 << 1（同规则回卷异或 0x87）
MAC  = 最后一块按 K1/K2 填充后走 CBC-MAC 式级联，输出取 128 位
```

测试向量（RFC 4493 的参数风格移植到 SM4，手册自算、复核脚本收录；OpenSSL 3.0 未提供独立 CMAC-SM4 实现可比对，以构造同构性 + 底层 SM4 KAT 保证正确性）：

```text
K    = 2B7E1516 28AED2A6 ABF71588 09CF4F3C
L    = 09CBE15D 851B5B0B BBA4CA42 EAE3FF70
K1   = 1397C2BB 0A36B617 77499485 D5C7FEE0
K2   = 272F8576 146D6C2E EE93290B AB8FFDC0

消息（复用 RFC 4493 的示例消息布局）              → CMAC-SM4
空消息                                            → 178AE41F 93EC6E9C 43086436 0932EF6B
6BC1BEE2…17393172A（16B 整块）                    → 4E4C2A44 17E567FE F081E0FA B55A5762
6BC1BEE2…E93D7E117393172A + 8B（40B 非整块）      → D221AD48 E4318A5B 308A91B9 15D7F75B
64 字节                                           → 6CE2999F 2464AEFE 04396323 135BA08C
```

（HMAC-SM3 与 CMAC-SM4 的分工：**HMAC-SM3 是协议栈首选**（TLCP 记录层、通用报文），**CMAC-SM4 偏向对称密钥体系内部**（密钥确认、IKE 类协议、无杂凑引擎的受限硬件）。）

## 3. 模式选择决策树

```text
需要认证吗？
├─ 否（仅保密）
│   ├─ 流式/网络 ───────────► CTR（配独立 MAC）或不用
│   └─ 存储扇区/行 ──────────► XTS；防细粒度篡改要求高 ─► HCTR
└─ 是（AEAD）
    ├─ 通用/高性能 ──────────► SM4-GCM（nonce 一次一用！）
    ├─ 受限硬件/短报文 ──────► SM4-CCM
    └─ nonce 可能复用 ───────► GCM-SIV（RFC 8452 形态）/ ZUC-MUR（GM/T 0001.4）
存储大对象 + 双向校验？
└─ 信封加密（GB/T 35275 数字信封）而不是直接选模式
```

## 4. 密评相关检查点

1. **模式选型**：出现明文 ECB 加密多分组数据、无认证的 CBC 用于不可信信道 → 整改项；
2. **IV/nonce 生成**：CBC 的 IV 必须随机（不可预测），CTR/GCM 的 nonce 必须唯一——来源要合规随机源或安全计数器；
3. **去填充实现**：抽查代码是否存在非常数时间的 unpad；
4. **单密钥用量**：GCM 超 2³² 分组、CBC 累计超限未换钥 → 风险项。
