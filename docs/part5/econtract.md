# 电子合同与存证出证全流程

电子合同是"密码技术 → 法律效力"映射最完整的场景：每一环密码组件都对应一条法律要件，最终在法庭上接受质证。本章把**业务链、法律链、密码链**三张图叠在一起讲——这也是密评章"电子签名法四要件"的工程展开版。

## 1. 业务全景：五环节

```text
① 实名认证 ──► ② 意愿确认 ──► ③ 签署 ──► ④ 存证 ──► ⑤ 出证
  是谁           真想签          签了什么     之后没被改    法庭能证明以上四步
```

任何一环缺失，证据链就断——司法判例中败诉的电子合同，几乎都是链条中间某环"只有业务动作、没有密码固化"。

## 2. 法律框架速查（条文级）

| 依据 | 条款 | 效果 |
| --- | --- | --- |
| 《电子签名法》（2005 施行，2015/2019 修正） | 第 13 条 | **可靠电子签名四要件**：制作数据专有、仅签名人控制、签名改动可发现、内容改动可发现（工程映射见密评章） |
| | 第 14 条 | 可靠电子签名与手写签名/盖章**同等法律效力** |
| | 第 5/6/7 条 | 数据电文的原件形式、保存要求、不得仅因电子形式被拒证 |
| | 第 16~18 条 | CA 须持电子认证服务许可（工信部）+ 国家密码管理机构使用密码证明——"两证"制度 |
| 《民法典》 | 第 469 条 | 数据电文**视为书面形式**（电子合同的形式合法性根基） |
| 最高法《关于互联网法院审理案件若干问题的规定》（2018） | 第 11 条 | 电子签名、可信时间戳、哈希值校验、区块链等技术固定的电子数据，**法院应当确认真实性** |
| 最高法《关于民事诉讼证据的若干规定》（2019 修订） | 第 15 条 | 与原件一致的副本/直接来源于电子数据的输出件**视为原件** |
| | 第 93/94 条 | 电子数据真实性的综合判断因素；**中立第三方平台**提供或确认的电子数据可确认真实性 |
| 最高法《人民法院在线诉讼规则》（2021 施行） | 第 12 条 | 经审核的电子化材料**视同原件**，可直接在线诉讼使用 |
| | 第 16/17 条 | 区块链存储数据**推定上链后未经篡改**；存证平台资质、利害关系、系统与技术的标准符合性为审查四要素 |

注意边界：电子签名法第 3 条排除**婚姻收养继承等人身关系、公用事业停止服务**等文书——这些场景电子签署不产生效力。

## 3. 逐环节的技术实现与密码组件

### 3.1 实名认证（"是谁"）

四要素（姓名+身份证号+手机号+银行卡）/人脸活体比对核验身份 → 平台或 CA 据此签发证书。密码角色：认证通道本身要过国密（TLCP），核验记录进证据链。

### 3.2 意愿确认（"真想签"）

短信验证码/刷脸/OAuth 授权 + 签署动作（手写笔迹采集/屏幕点击），全量留痕（时间、IP、设备指纹）。高频小额场景大量使用**事件型数字证书**——CA 针对每次签署行为签发短期证书，把"合同内容 + 场景信息（点击/划写动作）"一并加签固化。司法实践（锦天城等以案释法文献）对事件证书的效力总体认可，但**争议点在于它是"签名"还是"第三方见证"**——稳妥的做法是事件证书 + 通用证书/生物特征补强并用。

### 3.3 签署（"签了什么"）

```text
签署技术栈：
  文档层：OFD（GB/T 33190）/ PDF（GM/T 0112）版式文档
          + 电子签章（GB/T 38540：印章图像 + SM2 签名数据封装，见消息语法章）
  密码层：h = SM3(文档内容 ‖ 场景信息)；sig = SM2Sign(h)（证书 SM2withSM3）
  格式层：签名值 + 证书链 + 时间戳嵌入版式文档的签章结构
```

多签方流程：依次签（后者对含前者签名值的全文档再签），或使用 GB/T 35275 信封分发签约副本。**签名覆盖范围必须显式定义**（哪些字节进 SM3）——"签了文档没签附加条款"是高频诉讼争议。

### 3.4 存证（"之后没被改"）

三件套层层加固，各对应不同的证明力：

| 手段 | 标准/载体 | 证明力与注意 |
| --- | --- | --- |
| 哈希固化 | SM3 摘要 + 链式日志（每条日志含前条哈希） | 平台自证；防内部篡改 |
| 可信时间戳 | GM/T 0033（国家授时中心溯源，见消息语法章） | 证明"该内容在该时刻已存在"；TSA 令牌经 SM2 签名 |
| 区块链上链 | GM/T 0111（区块链密码应用）+ 最高法司法链/互联网法院平台对接 | **推定上链后未篡改**（在线诉讼规则 16 条）；上链前真实性仍需审查（17 条四要素：平台资质、无利害关系、系统标准符合、技术标准符合）——上链的通常只是哈希，原文件仍在平台 |

实操经验：上链数据 = 文档哈希 + 签名值哈希 + 全流程日志哈希的 Merkle 根；链上放摘要、链下存原件，出证时现场重算哈希与链上比对。存证成本已极低（单次数元级），相对公证（数百元/次）是数量级优势。

### 3.5 出证（"法庭能证明"）

出证形态：存证证明书 + 哈希/时间戳/上链核验记录 + CA 验签报告 + （必要时）公证书（部分平台与公证处打通后台出证通道）+ 平台原始数据当庭展示（证据规定 15 条的"原件"路径）。互联网法院对接平台可直接数据导入诉讼平台。

## 5. 反例模式（败诉案件的共性）

1. **只有短信验证码没有数字签名**——"意愿"有了，"签署"没固化，被认定未达成可靠电子签名；
2. **签名覆盖范围不含附件/费率表**——主文档有效、争议部分无签名；
3. **日志未做密码固化**——平台数据被质疑"可以事后修改"（证据规定 93 条的系统可靠性审查过不了）；
4. **利害关系平台自存自证**——平台是交易一方关联企业时，中立性被击穿（94 条的"中立第三方"不成立）；
5. **上链前环节空白**——只说"区块链不可篡改"，但"进链前的数据从哪来"没有证据（在线诉讼规则 17 条第 2 项）。

## 6. 平台自身的密评

电子合同平台按等保三级 + 密评建设的常态：CA 通道（两证核验）、时间戳（TSA 持证）、签名服务（密码机内 SM2 私钥）、存证库（SM4 加密 + SM3 完整性）、全链路日志完整性——对应 GB/T 39786 的应用和数据层面逐项展开（见密评章）。司法采信与密评结论在同一个证据链上互相加强：密评过的系统，其"系统环境可靠性"（93 条第一项）举证成本显著降低。
