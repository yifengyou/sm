# 附录 B：常见问题 FAQ

按"被问到频率"排序的实战问答。排错类问题均对应本书相应章节的展开论述。

## 算法与实现

**Q1：SM4 和 SMS4 是什么关系？**
SMS4 是 WAPI 时代的旧名（2006 年前后随 WAPI 实施细则流出），2012 年以 GM/T 0002-2012 正式发布时定名 SM4，两者是同一算法（见 VPN 章 WAPI 一节）。

**Q2：SM2 验签一直失败，签名值本身没问题，为什么？**
按概率检查三件事：① 双方签名 ID 不一致（一方缺省 `"1234567812345678"`、一方传了自定义 ID，导致 Z 值不同——最常见）；② 签名编码不一致（DER vs 64 字节裸 r‖s）；③ 验签方没做公钥点校验却遇到非法点。见 SM2 章排错表。

**Q3：A 库 SM2 加密，B 库解不开？**
九成是密文格式：旧序 C1‖C2‖C3 vs 国标新序 C1‖C3‖C2，以及 DER 封装 vs 裸字节。联调用 SM2 章的可复现示例密文对跑。

**Q4：SM4 软件性能为什么比 AES 慢？什么时候能追平？**
AES 有 AES-NI 专用指令（10 轮全硬件），SM4 是 32 轮查表/bitslicing——无指令支持时约为 AES 的 1/3~1/5。追平点已到：Intel Lunar Lake/Arrow Lake S 起提供 SM4 指令扩展（OpenSSL 3.6+ 支持，官方数据 CBC 约 3.6× 提升），鲲鹏/龙芯及 RISC-V Zvksed 亦有路径。选型前在目标平台实测。

**Q5：SM2 私钥 256 位，为什么说安全强度只有 128 位？**
安全强度按"最优攻击的工作量"计：256 位曲线上的 ECDLP 存在 √n 复杂度的 Pollard rho 类攻击，故强度约为阶的一半（2¹²⁸）——与 P-256、AES-128 同级，这是设计目标而非缺陷。

**Q6：随机数用 `/dev/urandom` 真的不安全吗？**
工程上现代内核熵池是健全的；问题在**合规**——它不属于经认证的密码产品/模块，密评按"随机数来源不合规"开整改项。用密码设备随机数接口或符合 GM/T 0105 的认证模块。见随机数章。

**Q7：SM1 还能用吗？**
存量硬件（加密卡/老网关）里继续跑，新系统没有任何理由主动选它。见 SM1 章。

**Q8：国密和 FIPS/国际算法能在同一系统共存吗？**
能，而且这是主流形态（双栈）。C 侧用 OpenSSL/Tongsuo 的多 provider 与属性查询，Java 侧 BC 与 SunRsaSign 等多 Provider 并存，Go 侧 gmsm 与标准库同用。注意证书与套件协商按客户端能力分流，防"被降级"。

## 证书与协议

**Q9：国密 HTTPS 选 TLCP 还是 TLS 1.3 + RFC 8998？**
对内/政务/金融存量生态 → TLCP（双证书是合规基线）；新国际化系统或追求 1-RTT/单证书运维 → RFC 8998（需确认监管接受度）。两套可并行部署。见 TLCP 章对照表。

**Q10：双证书可以只用一把私钥吗？**
不行也不合规：证书的 KeyUsage 扩展会区分职能，TLCP 握手按位置取用证书（签名在前、加密在后），一把私钥两用会在用途检查与密评中同时被卡。

**Q11：TLCP 握手失败，从哪里开始查？**
顺序：版本号（0x0101）→ 套件交集（GCM vs CBC）→ 双证书顺序与用途 → ClientKeyExchange 的 SM2 密文封装格式 → ECDHE 的签名覆盖范围。见 TLCP 章排错清单。

**Q12：证书快到期，两张证书到期日不一样怎么办？**
分开监控告警（这是运维事故高发点）；换发时签名证书应换新密钥对，加密证书按 KMC 策略延续或重新托管。见密钥管理章。

## 合规与密评

**Q13：等保三级系统不做密评有什么后果？**
属于"应评未评"，在监管检查/关基认定中是明确的合规缺口，且影响等保测评结论与后续整改周期；关基运营者则有每年至少一次的法定义务。见密评章。

**Q14：密评必须买密码机吗？**
不一定，但必须满足：随机数来源合规、密钥管理合规、密码产品持证。轻量系统可用带认证的密码模块（软件形态）；高等级系统实际上都会落到密码机/加密卡。先做自查清单再定采购。

**Q15：自研实现了 SM4，密评认吗？**
算法对不等于合规：自研实现需嵌入经认证的密码模块体系，或整体作为密码产品送检认证。业务层直接调用"魔改/自实现"算法是最常见的整改项之一。

**Q16：什么是"密码应用方案评估"？和密评什么关系？**
方案评估在规划阶段审《密码应用方案》（防建成即不合规），密评在建成运行后测实际效果。新建三级+系统强烈建议先过方案评估，成本差一个数量级。

## 选型与生态

**Q17：服务端国密支持选哪个库？**
TLCP 场景：Tongsuo（nginx/Tengine 集成、CLI 完整）。应用层算法：按语言选 GmSSL/BC/gmsm。见工程章全景表。

**Q18：手机 App 里怎么用国密证书？**
三种路线按安全等级选：UKey/ SIM-Key（最高，体验差）→ TEE/SE 内置密钥 → 协同签名（无硬件介质、密钥不完整存在于任何一方，主流金融 App 方案；已有行标 GM/T 0144-2025 可作为对接依据）。见密钥管理章协同签名一节。

**Q19：SM9 的 KGC 被攻破怎么办？**
这是体系级事件：所有由该主密钥派生的私钥全部失效，需要换主密钥并全量重发。预案：主密钥门限分片（多 KGC）、标识内嵌有效期、PQC 预案（配对密码在量子时代整体退场）。见 SM9 章。

**Q20：ZUC 和 SM4 怎么选？**
通用软件/存储/通道加密一律 SM4（模式丰富、生态全）；ZUC 的主场在电信（3GPP EEA3/EIA3 合规）与流式大吞吐场景（GB/T 33133 体系内），以及需要 256 位密钥量级的 ZUC-256。

**Q21：可信时间戳怎么做才合规？**
不能用本地 `time()` 或数据库时间字段自证时间。合规做法：接入选入认证目录的可信时间戳服务（TSA，GM/T 0033 体系），本地算 SM3 摘要送签，归档令牌并校验证书链与摘要一致性。见消息语法章时间戳一节。

**Q22：手册里的算法流程和测试向量，有办法一键自测吗？**
仓库附带 `scripts/verify_test_vectors.py`（纯 Python 标准库、零依赖，76 项）与 `scripts/verify_sm9_pairing.py`（SM9 配对驱动分量，依赖 gmalg，11 项）：覆盖 SM3/SM4/ZUC 官方 KAT、SM4 全部 32 个轮密钥、HMAC-SM3 三组（OpenSSL 交叉复核）、CMAC-SM4 子密钥与四组消息、EEA3 官方两例与 EIA3 示例 1/2（含 577 bit 完整消息）、HKDF-SM3 两组（OpenSSL kdf 交叉复核）、RFC 8998 的 SM4-GCM/CCM 向量、SM2 曲线自检与签名/加密/密钥交换/确定性签名（RFC 6979 结构）数值示例全链路、SM9 标准附录 A~D 的全部非配对分量 + 签名 h/KEM 与加密 K 等配对分量（gmalg 交叉复核）。两个脚本全绿即通过。

**Q23：密码模块安全等级怎么选？一级是不是不够用？**
等级与被保护系统的等级匹配即可（GB/T 39786 映射）：应用内嵌加密用一~二级软件模块足够，服务器密码机二~三级，KMC/CA 根密钥场景三级以上。盲目上四级徒增采购与运维成本。见密码模块章。

**Q24：SSH 远程运维怎么过密评？**
三条路线：改走国密 VPN/零信任网关（最常见）、采购带认证证书的 SSH 安全网关/堡垒机（对接可引用行标 GM/T 0129-2023《SSH 密码协议规范》）、自编译 OpenSSH 国密扩展（无证书，仅限过渡）。见 VPN 章远程运维一节。

**Q25：口令加密私钥文件，用 PBKDF2-SM3 可以吗？**
工程可行（OpenSSL 3.x `enc -pbkdf2 -md sm3` 直接支持，手册实测）。注意两点：跨库互操作要对齐参数（盐、迭代次数）；GB/T 35276 的私钥口令封装内部走国密 KDF 而非 PBKDF2，两者结构不同，不能混用。见密钥管理章 KDF 一节。

**Q26：电子合同上的国密签名，法院认吗？**
认，前提是构成《电子签名法》第十三条的"可靠电子签名"四要件：私钥专有、仅签名人控制、签名改动可发现、内容改动可发现。持牌 CA 证书 + 可信时间戳 + 第三方存证（含区块链上链，最高法在线诉讼规则已确立"上链后未篡改"推定）是最稳组合。完整流程（实名→意愿→签署→存证→出证）与败诉反例见电子合同章。

**Q27：数据安全法/个人信息保护法强制用国密吗？**
两部法只要求"采取加密等安全技术措施"，本身不指定算法族；数据落到等保三级/关基场景时，加密措施才依密码法体系收敛为商用密码。合规链条是：个保法/数安法 → 等保/关基 → 密码法/GB/T 39786 → 国密。见第一部分法律生态一节。

**Q28：系统上云了，"密码产品持证"怎么落地？**
组合拳：云密码机（带认证证书的 SDF 服务化实例）承担根密钥与高价值运算 + 认证软件模块内嵌应用。云厂商提供承载与编排，**密钥边界仍要落在你自己控制的持证模块内**。平台化形态与责任共担边界的展开见密码服务平台章。见密码模块章与工程章。

**Q29：工厂/电厂的老系统（Modbus、IEC 104，设备不能动）怎么过国密改造？**
不在协议和设备上下手，在边界上做：生产网与管理网之间、厂站与上级之间的链路用国密网关/纵向加密装置做隧道（SM2 认证 + SM4 加密），终端侧能加 ESAM 类安全模块的尽量加。密评时哑设备相关测评单元可判"不适用"，但边界保护必须实打实存在。完整路线抉择见工控章。

**Q30：该直接接密码机，还是建/买密码服务平台？**
只有一个系统且无多租户需求：密码机直连（SDF）可作为过渡。两个以上系统、或要过密评整改、或要统一审计与密钥治理：上平台——接口统一（GM/T 0019 SDK / 0136 HTTP）、密钥句柄化托管、审计汇聚，长期成本反而低。选型对比与"密钥不出平台"论证边界见密码服务平台章。


**Q31：网上说 TLCP 的行标是 GM/T 0054-2018，对吗？**
不对，这是流传很广的编号讹传。GM/T 0054-2018 实为《信息系统密码应用基本要求》（GB/T 39786-2021 的前身，密评的技术标尺）；TLCP 的协议前身是 **GM/T 0024-2014《SSL VPN 技术规范》**（GB/T 38636 基于其协议部分修改增加算法套件而来），TLCP 没有独立的行标版。依据：国家密码管理局官网标准目录与密标委《密码标准使用指南》。对照表见 TLCP 章与附录 A。

**Q32：想验证 SM9 的配对实现，手册能直接用吗？**
能。`scripts/verify_sm9_pairing.py`（依赖纯 Python 的 gmalg 库）已把标准附录 A 的签名 h、附录 C/D 的配对驱动 K 全部程序复现（11 项检查），自研配对实现后跑它即可定位"配对/KDF/点运算"哪一层出错；`scripts/verify_test_vectors.py`（零依赖，76 项）覆盖全部非配对分量。两个脚本的关系与用法见 SM9 章与工程章 KAT 一节。
