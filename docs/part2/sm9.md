# SM9 标识密码算法

SM9 是国密体系中最具特色的算法——**标识密码（Identity-Based Cryptography, IBC）**：用户的邮箱、手机号、设备 ID 等标识**本身就是公钥**，无需数字证书。标准为 **GB/T 38635-2020（原 GM/T 0044-2016）**，2021 年其数字签名部分进入 ISO/IEC 14888-3 国际标准。

代价与收益同样鲜明：IBC 免掉了证书、CA 与证书链校验的整个复杂度，但引入了**密钥生成中心（KGC）**——它掌握主密钥，可以派生任何用户的私钥（天然的密钥托管模型）。理解这对矛盾，是理解 SM9 全部设计与应用边界的关键。

## 1. 数学基础：双线性对

### 1.1 什么是双线性对

设 G₁、G₂ 是阶为素数 n 的加法循环群（椭圆曲线点群），G_T 是阶为 n 的乘法群。双线性对是满足如下性质的映射 e: G₁ × G₂ → G_T：

```text
双线性： e([a]P, [b]Q) = e(P, Q)^{ab}      对任意整数 a, b
非退化： e(P, Q) ≠ 1（存在 P, Q 使其非单位元）
可计算： e 可在多项式时间算出
```

第一条性质是全部 IBC 构造的引擎：它把两个群里的标量乘"搬"到目标群里变成指数乘积，使"分别持有秘密 a、b 的双方"能在不泄露秘密的前提下对乘积 ab 达成一致——这正是"发送方用标识加密、只有 KGC 派生的私钥才能解出"的数学机制。

### 1.2 SM9 的曲线与配对参数

SM9 采用 **256 位 BN 曲线**（Barreto–Naehrig 曲线），全部参数由 GB/T 38635.1 固定为常数（实现者不得更换）：

| 元素 | 值 / 说明 |
| --- | --- |
| 曲线 E(F_p) | y² = x³ + b，**b = 5** |
| p | `B640000002A3A6F1D603AB4FF58EC74521F2934B1A7AEEDBE56F9B27E351457D`（= 36u⁴+36u³+24u²+6u+1，u = `600000000058F98A`） |
| n（群阶） | `B640000002A3A6F1D603AB4FF58EC74449F2934B18EA8BEEE56EE19CD69ECF25`（= 36u⁴+36u³+18u²+6u+1） |
| G₁ | E(F_p) 上 n 阶子群（基域运算，点运算最快），生成元 P₁ = (`93DE051D…`，完整值见下） |
| G₂ | 扭曲线 E'(F_p²): y² = x³ + 5u 上的 n 阶子群（F_p² = F_p[u]/(u²+2)），运算最慢 |
| G_T | F_p¹² 中的 n 阶子群（嵌入度 k = 12） |
| e | 基于 BN 曲线的双线性对（Tate/R-ate 类配对） |

生成元的完整坐标（供实现自检）：

```text
P₁ = ( x = 93DE051D62BF718FF5ED0704487D01D6E1E4086909DC3280E8C4E4817C66DDDD
        y = 21FE8DDA4F21E607631065125C395BBC1C1C00CBFA6024350C464CD70A3EA616 )

P₂ = ( x = 37227552…AF82D65B + 85AEF3D0…D8806141·u        # F_p² 元素（r + w·u）
        y = A7CF28D5…C999A7C7 + 17509B09…84EBEB96·u )
      完整 128 字节值见 GB/T 38635.1 或本仓库复核脚本 scripts/verify_test_vectors.py
```

> 自检：验证 P₁ 满足 y² ≡ x³+5 (mod p)、[n]P₁ = O、P₂ 在扭曲线 y² = x³+5u 上且 [n]P₂ = O——复核脚本已内置这四项检查。

**嵌入度 k = 12 的含义**：配对把 ECDLP"搬运"到有限域 F_p^k 的乘法群中（MOV 归约）。若 k 太小（如超奇异曲线的 k≤6），子群上的 DLP 就会被域上 index calculus 攻击击穿，安全性崩塌；BN 曲线取 k=12，经典估计下使 256 位曲线在配对映射下保持约 128 位安全强度（2016 年 exTNFS 提出后学界下修至约 100~110 位，详见 6.1 节）——**IBC 曲线选型比普通 ECC 苛刻得多**，这是"不能随便拿一条 SM2 曲线做 IBC"的根本原因。

**工程代价**：配对运算是 SM9 所有操作中最贵的构件（软件实现毫秒量级，约为一次 SM2 标量乘的十倍上下），F_p¹² 乘法、扭曲线点运算的实现门槛显著高于普通 ECC。这也解释了 SM9 的软硬生态远薄于 SM2/SM3/SM4。

## 2. 体系结构与密钥派生

### 2.1 角色与主密钥

```text
KGC（密钥生成中心）：
  为"签名"与"加密/密钥交换"分别维护独立主密钥（密钥交换复用加密主密钥体系）：
    签名主私钥 s ←R [1, n−1]，  主公钥 P_pub-s = [s]P₂    （G₂ 上的点）
    加密主私钥 ke ←R [1, n−1]，主公钥 P_pub-e = [ke]P₁   （G₁ 上的点）
  主公钥是全系统公开参数；主私钥是全系统信任之锚
  （注意两组主公钥所在群的指派正好相反，跨库对接时序列化长度差一倍即此原因）
```

### 2.2 用户密钥派生（以标识 ID、识别符 hid 为输入）

hid 的取值（GB/T 41389-2022）：**签名 = 0x01，密钥交换 = 0x02，加密 = 0x03**。

```text
1. h = H1( ID ‖ hid )              # 杂凑到整数（构造见下）
2. 边界检查：h + d ≢ 0 (mod n)     # d 为主私钥 s 或 ke；违反则须重新生成主密钥
3. t = d · (h + d)⁻¹ mod n         # 私钥标量——注意是 d/(h+d)，不是 (h+d)⁻¹
4. KGC 经安全信道下发用户私钥：
     签名私钥 d_A = [t]P₁ ∈ G₁
     加密私钥 de_B = [t]P₂ ∈ G₂
5. 对应的"用户公钥"（供配对使用，任何人可自行计算——标识即公钥，免证书）：
     签名侧 P_A = [h]P₂ + P_pub-s ∈ G₂
     加密侧 Q_B = [h]P₁ + P_pub-e ∈ G₁   # 混合了标识与主公钥，不是单纯的 [h]P₁
```

**H1/H2 的精确构造**（GB/T 38635.1，与 SM2 的 Z 值完全不同）：

```text
Ha = SM3( 0x01 ‖ Z ‖ ct₃₂ ) ‖ SM3( 0x01 ‖ Z ‖ ct₃₂+1 )     # ct 为 4 字节大端计数器，取 1、2
h  = ( int( Ha 的前 40 字节 ) mod (n−1) ) + 1              # 归约到 [1, n−1]，保证非零
H2 同构，前缀字节换为 0x02；Z = ID‖hid（密钥派生）或 M‖w（签名）
```

结构解读：

- **私钥标量 t = d/(h+d)**：主私钥以可逆方式"编织"进用户私钥——验证方程（见下）正是靠 t·(h+d) ≡ d 这一代数关系闭环的；
- **用户公钥是 [h]P + P_pub**（不是单纯 [h]P）：标识哈希与主公钥相加后进入所有协议方程，**身份串是被密码学绑定的，不是带外声明**；身份或 hid 错一个字节，整个协议即失败；
- **私钥必须经 KGC**：t 的计算需要主私钥 d，用户自己无法生成——所以 KGC 天然知道所有用户私钥（托管）；
- **撤销怎么做**：标准做法是把有效期并入标识（如 `alice@example.com|2030-12-31`），过期后 KGC 不再派发新私钥，旧私钥自然失效——撤销问题转化为密钥派发策略问题；
- **工程陷阱（实测教训）**：把 H1 的归约 `(mod (n−1)) + 1` 误写成 `mod n`，实现内部依然自洽（自己签自己验能通过），但与标准附录 A 的数值示例对不上、跨实现互操作必挂——接入任何 SM9 库后第一件事应跑标准附录 A 的 d_A/S 示例（本仓库复核脚本已内置）。

## 3. 数字签名

SM9 签名输出二元组 **(h, S)**：h 是杂凑值，S 是 G₁ 上的点。预备常量：**g = e(P₁, P_pub-s)**（GT 中固定的配对基值）。

```text
签名（A，持有 d_A = [t_A]P₁）：
1. r ←R [1, n−1]
2. w = g^r                        # GT 中的幂
3. h = H2( M ‖ w )                # 杂凑到整数（构造同 H1，前缀字节 0x02）
4. l = (r − h) mod n；l = 0 则回到 1
5. S = [l]·d_A                    # G₁ 点
6. 输出 σ = (h, S)

验签（任何验证者）：
1. 校验 h ∈ [1, n−1]，S ∈ G₁、在曲线上且非无穷远点
2. h_A = H1( ID_A ‖ hid )
3. w′ = e( S, [h_A]P₂ + P_pub-s ) · g^h     # 配对第二分量在 G₂
4. 校验 h = H2( M ‖ w′ )，相等则通过
```

**正确性**（代数闭环）：私钥标量 t_A 满足 t_A·(s + h_A) ≡ s (mod n)。记 g₀ = e(P₁, P₂)，则 g = e(P₁, [s]P₂) = g₀^s：

```text
e(S, [h_A+s]P₂) = e([l·t_A]P₁, [s+h_A]P₂) = g₀^{l·t_A·(s+h_A)} = g₀^{l·s}
g^h = g₀^{s·h}
w′ = g₀^{l·s + s·h} = g₀^{s·(l+h)} = g₀^{s·r} = g^r = w  ✓  于是 H2(M‖w′) = h
```

这正是 2.2 节私钥标量取 t = d/(h+d) 的用途：KGC 把主私钥以可逆方式织入用户私钥，验证方仅凭公开量（[h_A]P₂ + P_pub-s 与 g^h）即可复原 g^r。

与 BLS 签名对比：BLS 是 σ = [H(m)]sk 的纯配对等值检查（签名极短）；SM9 引入随机数 r 与杂凑 h，形式上更接近"把 Schnorr 协议搬进 GT"，签名是 (h, 点S) 两元组而非单个点。

## 4. 密钥封装与公钥加密（KEM + DEM + MAC）

### 4.1 密钥封装机制（KEM）

```text
封装（发送方 → 标识 ID_B）：
1. Q_B = [h_B]P₁ + P_pub-e             # 用户加密公钥（G₁，混合标识与主公钥）
2. r ←R [1, n−1]
3. C₁ = [r]·Q_B                        # 封装密文分量（G₁ 点）
4. w = e( P_pub-e, P₂ )^r              # 配对基值 = 加密主公钥 × P₂
5. K = KDF( C₁ ‖ w ‖ ID_B, klen )      # KDF 输入包含接收方标识！
6. 输出 (C₁, K)，K 为双方共享的对称密钥

解封（接收方 B，持有 de_B = [t_B]P₂，t_B = ke·(ke+h_B)⁻¹）：
1. w′ = e( C₁, de_B )
   = e( [r·(h_B+ke)]P₁, [t_B]P₂ ) = g₀^{r·(h_B+ke)·t_B} = g₀^{r·ke} = w  ✓
2. K = KDF( C₁ ‖ w′ ‖ ID_B, klen )
```

正确性一目了然：`(h_B+ke)·t_B ≡ ke`，解封方由此复原发送方的 w。第三方没有 ke，算不出 w——这就是"标识加密"的全部魔法。

### 4.2 公钥加密 = KEM + DEM + MAC（GB/T 38635.2）

```text
加密：
  取 klen = |M| + 32（比消息多派生 32 字节 MAC 密钥）
  K  = KDF( C₁ ‖ w ‖ ID_B, |M| + 32 )
  C₂ = M ⊕ K[0..|M|)
  C₃ = SM3( C₂ ‖ K[|M|..] )            # MAC 分量
  C  = C₁ ‖ C₃ ‖ C₂

解密：
  解封得 K → M′ = C₂ ⊕ K[0..|M|)
  校验 SM3( C₂ ‖ K[|M|..] ) = C₃，失败则拒绝
```

注意点：

- **C₃ = SM3(C₂ ‖ K₂)**——与 SM2 加密的 C₃ = SM3(x₂‖M‖y₂) 结构完全不同，从 SM2 迁移到 SM9 时的高发混淆点；
- **KDF 输入包含 ID_B**（SM2 的 KDF 只吃 x₂‖y₂）：接收方标识参与密钥派生，标识错一个字节解密即失败；
- C₁ 常序列化为 64 字节裸坐标（G₁ 点，不带 0x04 前缀，gmsm/GmSSL 惯例），也有带前缀的封装，跨库对接需先确认；
- KEM 的随机数 r 一次一用，重用会破坏机密性；
- DEM 层：GB/T 41389-2022 允许 SM4-CBC/GCM 等作为 DEM，但**非 XOR 型 DEM 的 IV 传递方式标准未作强约束**，跨实现互操作需显式约定 IV 来源与封装位置；
- 消息长度基本不受限（DEM 承担数据加密），这一点与 SM2 加密的 KDF 一次一密结构一致。

## 5. 密钥交换

SM9 密钥交换（IBK，hid = 0x02）**复用加密主密钥体系**（同一 P_pub-e 与用户加密私钥），双方各持临时随机数完成协商（A 为发起方）：

```text
预备：g = e(P_pub-e, P₂)；A 持 de_A，B 持 de_B

A1  r_A ←R [1, n−1]
A2  R_A = [r_A]·( [h_B]P₁ + P_pub-e )      # 在对方（B）的用户公钥上乘临时密钥
A3  （收到 R_B 后）g₁ = g^{r_A}；g₂ = e(R_B, de_A)；g₃ = g₂^{r_A}
A4  K = KDF( ID_A ‖ ID_B ‖ R_A ‖ R_B ‖ g₁ ‖ g₂ ‖ g₃, klen )

B 侧对称：R_B = [r_B]·( [h_A]P₁ + P_pub-e )，
    g₁′ = g^{r_B}，g₂′ = e(R_A, de_B)，g₃′ = g₂′^{r_B}
    K = KDF( ID_A ‖ ID_B ‖ R_A ‖ R_B ‖ g₂′ ‖ g₁′ ‖ g₃′, klen )
                                            # 注意 B 侧 g₁/g₂ 顺序对调（原因见下）
（可选）S_A/S_B 密钥确认值：0x82/0x83 前缀区分方向，
        覆盖 g₂、g₃ 与双方标识、双方临时公钥
```

- **"对调"的代数原因**：g₂(A) = e(R_B, de_A) = g₀^{ke·r_B} 恰好等于 g₁′(B)，g₁(A) = g^{r_A} = g₀^{ke·r_A} 恰好等于 g₂′(B)——双方各自算出的两个 GT 值互为镜像，B 侧在 KDF 输入中把 g₁′/g₂′ 对调后，两方输入才完全一致（漏掉这个对调是 SM9 密钥交换的经典实现 bug）；
- 附录 B 示例（Alice/Bob，r_A/r_B 见标准）：16 字节会话密钥 = `C5C13A8F59A97CDEAE64F16A2272A9E7`（R_A 等非配对中间量已程序复核，GT 分量以标准文本为准）；
- 双方身份通过标识私钥的持有性**隐式认证**（配对方程闭环即证明对方持有该标识的私钥）；
- 与所有 IBC 一样，**KGC 能冒充任何用户参与协议**（它有全部私钥）——对 KGC 的信任是前提而非结论；
- 高安全等级系统若不能接受托管，应改用 SM2/TLS 的"证书 + (EC)DHE"路线。

## 6. 安全性分析

### 6.1 算法与参数层

- 安全性同时依赖三件事：BN 曲线 ECDLP、F_p¹² 乘法群 DLP（配对搬移后）、以及 KDF/杂凑的 SM3。k=12 的嵌入度是参数安全的命门——SM9 的曲线参数由标准固定，**实现者绝不可自行更换曲线**（低嵌入度或非扭安全曲线会直接击穿体系）；
- **安全强度的再评估**：BN-256 曲线的经典估计为 128 位（3072 位扩域），但 Kim–Barbulescu（2016）的 exTNFS 算法利用扩域结构显著加速了 NFS 求解，学界把 256 位 BN 曲线的实际强度修正到约 100~110 位量级（具体数字仍有争议）——低于 128 位现代目标，大致处于 RSA-2048 的安全量级。对保密寿命长的数据，这是比 KGC 托管更需要提前规划的数学层面约束；
- 公开分析未发现对完整 SM9 的有效攻击。

### 6.2 体系层（IBC 特有的风险面）

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| **KGC 托管** | 主私钥持有者可派生任何用户私钥、解密任何历史密文、冒充任何人签名 | 主密钥分片/门限化（多 KGC 联合）、托管协议与审计、敏感场景改用 PKI |
| 主密钥泄露 | 灾难级：全系统私钥可重算、历史签名可伪造（若不绑时间） | 硬件保护（HSM）、主密钥备份的物理安全、标识含有效期限定爆炸半径 |
| 私钥分发信道 | 私钥经 KGC→用户的通道下发，通道被截即失守 | 离线发key仪式/加密下发+口令封装（如 PBE） |
| 撤销与有效期 | 无 CRL/OCSP 对应物，撤销靠"标识里带有效期+停止派发" | 派发策略系统化、短周期标识 |

### 6.3 实现层

- **公钥/私钥点校验**：配对函数对"不在正确子群里的点"可能仍给出结果，必须先验证点在正确 n 阶子群（防无效曲线/小子群攻击）；
- **配对实现侧信道**：配对是长而复杂的多项式求值链，时序/功耗泄漏面大，高价值场景用常数时间实现或硬件；
- 兼容性：G₂/F_p¹² 运算实现细节多（塔式扩域、扭曲线坐标），跨库联调前先对跑标准 KAT。

## 7. 性能画像（数量级）

| 操作 | 主要开销 | 相对量级（软实现） |
| --- | --- | --- |
| 用户私钥生成（KGC） | 1 次逆元 + 1 次标量乘 | ≈ SM2 一次签名 |
| 签名 | 1 次 GT 指数 + 1 次标量乘 | ≈ 10× SM2 签名 |
| 验签 | 1 次配对 + 1 次 GT 指数 | ≈ 10× SM2 验签 |
| 封装/解封 | 1 次配对（或 1 次 GT 指数） | ≈ 10× SM2 加密 |

结论：SM9 是"用计算换证书体系"的算法——省掉 PKI 的证书签发、分发、链校验、撤销基础设施，付出每次操作约一个数量级的公钥运算开销。大批量高频场景（每笔交易都验签）对成本敏感时，SM2+证书往往更划算。

## 8. 应用场景与生态

| 场景 | 为什么适合 SM9 |
| --- | --- |
| 物联网/设备标识加密 | 设备出厂无证书负担，用设备 ID 直接加密下发指令/密钥 |
| 邮件/文档标识加密 | 收件人邮箱即公钥，无需先拿到对方证书 |
| 通信标识（手机号）安全 | 号码即标识，电信场景天然匹配 |
| 区块链标识密钥 | 账户地址/链上 DID 即标识，KGC 可由联盟共治（门限主密钥） |
| 电子印章/签章系统 | 印章标识绑定签发主体，简化证书链 |

实现生态：BouncyCastle（SM9 全套）、GmSSL、Tongsuo、gmsm（Go，含与 GmSSL/BC 的互操作验证）、gmalg（纯 Python）等均提供 SM9；密钥、签名与密文的编码格式遵循 **GB/T 41389-2022《SM9 密码算法使用规范》**（ASN.1 封装及测试用例），密钥管理系统建设参照 **GM/T 0086-2020**；硬件层面支持 SM9 的密码卡/密码机少于 SM2/SM4，选型时需专项确认（合规项目中还应确认产品认证证书覆盖 SM9）。

## 9. SM9 vs PKI（SM2）选型对照

| 维度 | SM9（IBC） | SM2 + 证书（PKI） |
| --- | --- | --- |
| 公钥获取 | 标识即可（零基础设施） | 需证书分发与链校验 |
| 信任模型 | KGC 全知（托管） | CA 只证明公钥归属（不知私钥） |
| 撤销 | 派发策略 + 有效期进标识 | CRL/OCSP 成熟机制 |
| 性能 | 配对昂贵（~10×） | 普通 ECC |
| 合规成熟度 | 场景化使用 | 主流通用方案 |
| 典型选择 | 海量弱设备、标识天然存在的封闭体系 | 开放互联网、高安全等级系统 |
