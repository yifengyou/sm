# SM2 椭圆曲线公钥密码算法

SM2 是国密体系的公钥密码基石，标准为 **GB/T 32918（原 GM/T 0003-2012）**，共 5 部分：

| 部分 | 内容 | 对应国际机制 |
| --- | --- | --- |
| Part 1 | 总则（数学基础与曲线参数） | SEC1/SEC2 |
| Part 2 | **数字签名算法** | ECDSA |
| Part 3 | **密钥交换协议** | ECDH + 身份确认 |
| Part 4 | **公钥加密算法** | ECIES |
| Part 5 | 参数定义（推荐曲线） | SEC 2 推荐曲线 |

SM2 签名已进入 ISO/IEC 14888-3 国际标准。本章先讲数学底座，再逐个拆解三个功能，最后给数值级示例与工程要点。

## 1. 数学基础：素域上的椭圆曲线

### 1.1 曲线方程

SM2 使用素域 `Fp` 上的短 Weierstrass 曲线：

```text
E: y² = x³ + ax + b   (mod p)，其中 4a³ + 27b² ≠ 0 (mod p)
```

曲线上所有点（含无穷远点 O）在"点加"运算下构成交换群：

- **点加**（P ≠ ±Q）：过 P、Q 作直线交曲线于第三点 R'，取其关于 x 轴的镜像 R = P + Q；
- **倍点**（P = Q）：过 P 作切线，同理取镜像得 2P；
- **标量乘**：`[k]P = P + P + … + P`（k 个 P 相加），是密码学使用的核心运算。

安全性的根基是**椭圆曲线离散对数问题（ECDLP）**：已知 P 和 Q = [k]P，求 k 在计算上不可行。256 位曲线上的 ECDLP 穷举复杂度约 2^128，因此 SM2 的安全强度是 **128 位**。

### 1.2 推荐曲线 sm2p256v1

GB/T 32918.5 只定义了一条 256 位推荐曲线 `sm2p256v1`（记号沿用标准）：

| 参数 | 值（十六进制，256 位） |
| --- | --- |
| p | `FFFFFFFE FFFFFFFF FFFFFFFF FFFFFFFF FFFFFFFF 00000000 FFFFFFFF FFFFFFFF` |
| a | `FFFFFFFE FFFFFFFF FFFFFFFF FFFFFFFF FFFFFFFF 00000000 FFFFFFFF FFFFFFFC`（即 p − 3） |
| b | `28E9FA9E 9D9F5E34 4D5A9E4B CF6509A7 F39789F5 15AB8F92 DDBCBD41 4D940E93` |
| n（群的素数阶） | `FFFFFFFE FFFFFFFF FFFFFFFF FFFFFFFF 7203DF6B 21C6052B 53BBF409 39D54123` |
| Gx | `32C4AE2C 1F198119 5F990446 6A39C994 8FE30BBF F2660BE1 715A4589 334C74C7` |
| Gy | `BC3736A2 F4F6779C 59BDCEE3 6B692153 D0A9877C C62A4740 02DF32E5 2139F0A0` |

设计要点：

- **p 是特殊形式的素数**，接近 2^256 满值，支持快速模约简（类比 NIST P-256 的快速约简），这是软件性能的关键；
- **a = p − 3**：减少点加/倍点中的乘法次数（3x² + a 的优化），NIST 曲线同款技巧；
- **余因子 h = 1**：曲线上的点数 #E(Fp) = n（素数），不存在小子群攻击面，公钥校验可以简化；
- G 的阶恰为 n，且 **[n]G = O**（无穷远点）。

> 自检：用任意大数库验证 `Gy² ≡ Gx³ + aGx + b (mod p)` 与 `[n]G = O`，是校验曲线参数抄录是否正确的两行代码。

### 1.3 密钥对

- **私钥**：d ∈ [1, n − 2] 的随机整数（256 位）；
- **公钥**：点 P = [d]G = (x_P, y_P)，未压缩序列化为 `04 ‖ x_P ‖ y_P`（65 字节），压缩形为 `02/03 ‖ x_P`（33 字节）；
- 公钥编码进 X.509 证书时使用**未压缩点**格式，曲线 OID 为 `1.2.156.10197.1.301`。

## 2. 预处理：Z 值——SM2 与 ECDSA 的第一个分水岭

ECDSA 直接对消息哈希签名；SM2 则先把**签名者身份与全部曲线参数**杂凑成一个 256 位的 Z 值，再与消息拼接后杂凑：

```text
Z_A = SM3( ENTL_A ‖ ID_A ‖ a ‖ b ‖ Gx ‖ Gy ‖ x_A ‖ y_A )

其中：
  ID_A —— 用户 A 的标识（字节串），缺省值为 ASCII "1234567812345678"
  ENTL_A —— ID_A 的比特长度，2 字节大端（缺省 ID 时为 0x0080）
  a, b, Gx, Gy —— 曲线参数（各 32 字节大端）
  x_A, y_A —— 签名者公钥坐标（各 32 字节大端）
```

Z 值的作用是**把"谁在签、在哪条曲线上签"绑进签名**：同一条消息在不同身份、不同曲线实现下的摘要不同，可以抵抗"曲线参数替换"与"身份混淆"类攻击，也让签名天然具备"上下文完整性"。

工程上最大的坑也在这里：**如果签名方与验签方的 ID 不一致（一方用缺省 ID，一方显式传了用户 ID），验签必然失败，且报错信息通常毫无提示**。跨库联调时 Z 值不匹配是 SM2 验签失败的第一大原因。

## 3. 数字签名算法（GB/T 32918.2）

### 3.1 签名

输入：消息 M、私钥 d_A、用户标识 ID_A。输出：签名 (r, s)。

```text
1. e = SM3(Z_A ‖ M)                       # 摘要（Z_A 见上节）
2. 随机 k ← [1, n−1]
3. (x₁, y₁) = [k]G
4. r = (e + x₁) mod n
   若 r = 0 或 r + k = n，回到 2
5. s = ((1 + d_A)⁻¹ · (k − r·d_A)) mod n
   若 s = 0，回到 2
6. 输出 (r, s)
```

### 3.2 验签

输入：M、签名 (r, s)、公钥 P_A、ID_A。

```text
1. 校验 r, s ∈ [1, n−1]，否则拒绝
2. e = SM3(Z_A ‖ M)                       # Z_A 用验签方重算，依赖双方 ID 一致
3. t = (r + s) mod n；t = 0 则拒绝
4. (x₁', y₁') = [s]G + [t]P_A
5. R = (e + x₁') mod n
6. R = r 则验签通过
```

**正确性**（为什么第 4 步能还原 x₁）：由 s = (1+d)⁻¹(k − rd) 可推出 k = s + t·d（t = r+s），于是 [s]G + [t]P_A = [s]G + [td]G = [k]G。验签只做一次"双标量乘"（2P-MUL），这是椭圆曲线签名的标准性能瓶颈。

### 3.3 与 ECDSA 的差异对照

| 维度 | ECDSA (P-256) | SM2 |
| --- | --- | --- |
| 消息摘要 | Hash(M)，与身份无关 | SM3(Z_A ‖ M)，绑定身份与曲线参数 |
| 签名方程 | s = k⁻¹(e + r·d) | s = (1+d)⁻¹(k − r·d) |
| 随机数 k 的位置 | 在求逆一侧 | 在被乘一侧 |
| 验签方程 | u₁G + u₂Q，u₁ = e·s⁻¹ | [s]G + [t]P_A，t = r+s |
| 哈希算法 | SHA 系列 | SM3 |
| 随机数风险 | k 泄露/重用 → 私钥恢复 | **完全相同的问题**（见安全性节） |

### 3.5 签名数据格式

- **DER（证书、TLCP 内）**：`SEQUENCE { INTEGER r, INTEGER s }`，与 ECDSA 相同的编码习惯（注意 r/s 高位为 1 时需补 `0x00`）；
- **Raw（许多应用层接口）**：定长 64 字节 `r ‖ s`；
- **带 SM2 恢复/标识信息的封装**：部分库（如 Go、Java BC）要求显式传入 UserID（即 ID_A），缺省时必须与对端约定一致。**实现差异是互操作故障高发区**。

**关于"公钥恢复"**：ECDSA（secp256k1）生态里的 recovery-id 机制让验签方从签名反推公钥，区块链场景重度使用。SM2 **标准未定义公钥恢复算法**，且 Z 值本身依赖公钥坐标（先有公钥才能算 Z、才能算 e），恢复比 ECDSA 多一层"先有鸡还是先有蛋"的问题。工程惯例是**显式携带**：交易/报文里放公钥或其 SM3 哈希，验签方据此构造 Z；需要恢复时由上层协议自行定义候选公钥枚举与校验流程。

### 3.6 确定性签名：把 k 从"随机数"变成"派生值"

随机数 k 是 SM2 签名的阿喀琉斯之踵（见安全性节）。合规首选是硬件设备内生成 k；纯软件场景的补救是**确定性签名**——把 RFC 6979 的 HMAC-DRBG 派生循环移植到 SM2：杂凑函数换 SM3，群的阶换成 SM2 的 n，待签摘要就是 e = SM3(Z_A ‖ M)：

```text
初始化：
  V = 0x01 × 32；K = 0x00 × 32
  K = HMAC-SM3(K, V ‖ 0x00 ‖ int2octets(d_A) ‖ int2octets(e mod n))
  V = HMAC-SM3(K, V)
  K = HMAC-SM3(K, V ‖ 0x01 ‖ int2octets(d_A) ‖ int2octets(e mod n))
  V = HMAC-SM3(K, V)
循环：
  生成 T：反复 V = HMAC-SM3(K, V)，拼接直到 |T| ≥ 256 位
  k = int(T) 的前 256 位
  若 k 合法且 r、s 检查通过 → 用该 k 完成标准 SM2 签名
  否则 K = HMAC-SM3(K, V ‖ 0x00)；V = HMAC-SM3(K, V)；重试
```

三点工程认知：

- **对验签方完全透明**：确定性派生只改变 k 的来源，签名 (r, s) 仍是标准 SM2 签名，任何普通验签实现都能验证——不存在"确定性签名互操作"问题；
- **GB/T 32918 并未规定此模式**，属社区通行的工程实践（RFC 6979 结构移植）；若所用库未内建，可在库外用上式派生 k，再调用底层库的"指定 k 签名"接口；
- 数值示例（复用 3.4 节的 d_A 与消息 `M = "message digest"`，缺省 ID）：

```text
确定性 k = 78F1C31494614F9931F7752C0E605982BA2D5CAA412CCA61FD5D0FB5DB34B66E
r = EA3A91414124E6D2A6BCB670FBCEE2931B9983FDE8739D36D21AD2CF25B48975
s = 30EDC7CAE5892B6A421A5C4FDDB229D2F485B9D9FA36848378AD7C99CBA860DB
（同一私钥对同一消息永远得到同一签名；可用复核脚本验证）
```

## 4. 密钥交换协议（GB/T 32918.3）

SM2 密钥交换可理解为"内建身份认证的 ECDH"：双方各持长期 SM2 密钥对，在协议内完成临时密钥交换与身份确认（类似 SIGMA/STS 的效果），最终双方获得共享密钥并互相确认对方身份。

### 4.1 流程（简化记号，A 为发起方）

```text
预备：A 持 (d_A, P_A)，B 持 (d_B, P_B)；各自计算 Z_A、Z_B（同签名预处理）

A → B:  RA = [r_A]G            # r_A 为 A 的临时私钥
B → A:  RB = [r_B]G            # r_B 为 B 的临时私钥，B 先完成如下计算再应答

B 侧：
  x̄_B = 2^w + (x_B & (2^w − 1))     # w = ⌈⌈log2 n⌉/2⌉ − 1，临时公钥 x 坐标的"折叠值"
  t_B = (d_B + x̄_B·r_B) mod n
  x̄_A 同理由 RA 计算
  V = [h·t_B](P_A + [x̄_A]RA)        # 共享点
  K_B = KDF(x_V ‖ y_V ‖ Z_A ‖ Z_B, klen)
  （可选）S_B = Hash(0x02 ‖ y_V ‖ Hash(x_V ‖ Z_A ‖ Z_B ‖ x̄_A ‖ x̄_B ‖ RB))

A 侧：对称地计算 V 与 K_A，并（可选）校验 S_B、生成 S_A 供 B 校验
```

要点：

- 临时公钥 x 坐标以 `2^w + 低 w 位` 的形式**同时混入双方的临时份额与长期私钥**，这一"密钥确认折叠"设计使协议在静态密钥场景下无需额外签名即可抵抗中间人；
- Z_A、Z_B 进入 KDF，**身份直接参与密钥派生**——身份串接错一个字节，双方得到的密钥就不同（表现为后续通信用密钥不一致）；
- S_A/S_B 是可选的**密钥确认**步骤（0x02/0x03 前缀区分方向），严格实现建议开启。

### 4.2 与 ECDH/ECDHE 的对比

| 维度 | ECDH/ECDHE | SM2 密钥交换 |
| --- | --- | --- |
| 身份认证 | 不内建（需外挂签名） | 内建（长期密钥 + Z 值） |
| 前向保密 | 仅 (EC)DHE 模式有 | 使用临时密钥 r_A/r_B 时具备 |
| 典型使用 | TLS 等协议的组合构件 | 专用安全通道、电子合同密钥协商等 |

实践中 TLCP 的 ECDHE 套件并没有直接使用本协议，而是"SM2 临时密钥 + 签名"的 TLS 风格组合（见 TLCP 章）；SM2 密钥交换更多用于应用层的点对点协商场景。

## 5. 公钥加密算法（GB/T 32918.4）

### 5.1 加密

输入：消息 M（klen 字节）、接收方公钥 P_B。输出密文 C：

```text
1. 随机 k ← [1, n−1]
2. C₁ = [k]G = (x₁, y₁)                        # 椭圆曲线点（65 字节未压缩）
3. (x₂, y₂) = [k]P_B                            # 共享秘密点
4. t = KDF(x₂ ‖ y₂, klen)                       # SM3 构造的 KDF，输出 klen 字节
   若 t 全零，回到 1
5. C₂ = M ⊕ t                                   # 一次一密式异或
6. C₃ = SM3(x₂ ‖ M ‖ y₂)                        # 摘要校验值（32 字节）
7. 输出 C = C₁ ‖ C₃ ‖ C₂                        # 新标准的字段顺序
```

### 5.2 解密

```text
1. 从 C 中取 C₁（曲线点，校验其在曲线上且阶为 n）
2. (x₂, y₂) = [d_B]C₁
3. t = KDF(x₂ ‖ y₂, klen)
4. M' = C₂ ⊕ t
5. 校验 SM3(x₂ ‖ M' ‖ y₂) = C₃，失败则拒绝       # 抗篡改/选择密文攻击
```

C₃ 的校验不可省略：它同时承担"密文完整性"和"公钥有效性确认"两个职责，是 SM2 加密在协议层抵抗主动攻击的关键（ECIES 中对应 MAC 的角色）。

### 5.3 KDF（GB/T 32918.1 附录）

SM2 体系的密钥派生函数全部采用"SM3 计数器模式"：

```text
KDF(Z, klen)：
  for ct = 1, 2, … ⌈klen/32⌉:
      b_ct = SM3(Z ‖ ct)         # ct 为 4 字节大端计数器
  返回 b₁ ‖ b₂ ‖ … 截取前 klen 字节
```

### 5.4 数值示例（可复现）

接收方私钥与消息（本节自选）：

```text

随机 k = 7E0E9A5C3F8B7D2A6E1F4C0B9D8A3E7215C6B0F4D2E8A1C3B7F9E5D04A6C2B88

C₁ = 04
     F5AF3EE5F35827F745419C3DBDC344B41F320FBC101D6984CF6F517CB7A23B67
     3458CD1538936CBC8967EDFE21720FDFDFBA14F6E8B14E9F8961D61476FD7858   （[k]G）
```

### 5.5 C1C2C3 还是 C1C3C2——最重要的互操作陷阱

- **旧 GM/T 0003-2012 时代约定：C = C₁ ‖ C₂ ‖ C₃**；
- **GB/T 32918.4（国标）调整为：C = C₁ ‖ C₃ ‖ C₂**（把校验值提前，利于流式处理时先验证再解密）；
- DER 封装（GM/T 0009）把三个字段编码为 `SEQUENCE { ECPoint C₁, OCTET STRING C₂/HASH C₃ }`，字段顺序在 ASN.1 里自描述，但**很多实现只支持裸字节序**。

现实中 GmSSL、Tongsuo、BouncyCastle、各类 HSM 各有默认值与开关（如 `-c1c3c2` / `CipherMode.C1C3C2`），**对接前必须先对齐密文格式**。一个实用的联调技巧：用本节示例的密文让对方解密，能解出 `encryption standard` 即格式一致。

## 6. 安全性分析

### 6.1 算法层

- SM2 的安全性归约到 sm2p256v1 上 ECDLP 的困难性。该曲线参数经过公开密码学界十余年分析，未发现结构性弱点（非超奇异、j-不变量正常、n 为素数、余因子 1、可抗 MOV/异常点攻击——这些"曲线体检"项都通过）。
- **实际攻击界**：ECDLP 的已知最优攻击是 Pollard rho（并行化约 2^128 群运算量级，远优于穷举私钥），与 128 位安全强度的设计目标一致——没有更快的方法，这是"十年无结构弱点"的量化表述。
- **参数如何生成**（外界常问、值得诚实回答的问题）：sm2p256v1 的参数由标准起草方给出，**标准文本未公开参数的生成过程与可验证随机性证明**。这并非孤例——NIST P 系列曲线同样经历过"种子来源信任"之争；对比之下 Brainpool 曲线族与 RFC 9380（hash-to-curve 与可验证曲线生成）提供了"参数可复现推导"的透明路线。社区的实际立场是：参数无结构弱点 + 十余年公开分析，风险评估可接受；对"不信任任何未公开生成过程"的场景，国密体系内目前没有官方备选曲线——选型时如实向评估方说明这一边界即可，不要自行换曲线（换成"自己生成的曲线"是远比信任标准参数更差的选择）。
- 签名/加密的随机数 k 是最薄弱环节：
  - **k 重用**（不同消息用同一个 k）：两份签名联立可线性解出私钥 d——2010 年索尼 PS3 ECDSA 私钥泄露即此因；
  - **k 部分泄露**（侧信道、随机数发生器偏置）：多项式恢复私钥的攻击已知（与 ECDSA 同类，LadderLeak 类边界攻击）；
  - 结论：**SM2 签名必须使用密码学安全的随机数或确定性签名（见 3.6 节）**，硬件设备内生成 k 是合规首选。

### 6.2 实现层（侧信道与无效曲线）

- 标量乘必须防时序/功耗/缓存侧信道：Montgomery ladder、坐标随机化、固定窗口的不变量访问模式；
- 验签与解密前必须做**公钥/密文点校验**（在曲线上、阶为 n、非无穷远点），否则可被"无效曲线攻击"逐步泄露静态私钥——SM2 余因子为 1 使校验便宜，没有理由省略；
- 解密中 C₃ 校验失败必须恒定时间拒绝，不能泄露失败的位置。

## 7. 实现与性能要点

- **定点乘法优化**：基点 G 是公开常数，可用 comb 方法预计算大规模表（如 4-bit 窗口表约 32KB），固定基点乘 [k]G 比随机基点乘快 30%–50%；签名中的 [k]G、加密中的 [k]G 都受益；
- **双标量乘**：验签的 [s]G + [t]P_A 用联合窗口（interleaving）或 Strauss-Shamir 技巧，比两次单乘快约 30%；
- **模约简**：利用 p 的特殊形式做快速约简（无需通用 Montgomery/Barrett），这是 SM2 软实现性能的基本盘；
- 量级参考：现代 x86 单核上，优化实现的 SM2 签名约为数万次/秒量级，验签略低于签名吞吐的一半；与 P-256 的差距主要来自生态（P-256 有更成熟的优化与指令加速）而非算法本身；
- 硬件路径：密码卡/密码机内建 SM2 引擎（GM/T 0018 SDF 的 `SDF_GenerateKeyPair_ECC`、`SDF_InternalSign_ECC` 等），合规系统建议密钥不出设备、仅传出签名结果。

## 8. 常见问题速查

| 现象 | 根因 |
| --- | --- |
| 验签失败，签名值本身正确 | 双方 ID 不一致（缺省 ID vs 自定义 ID），Z 值不匹配 |
| A 库加密 B 库解密失败 | C1C2C3/C1C3C2 顺序不一致，或 DER vs 裸格式不一致 |
| 随机偶发验签失败 | 签名端 k 生成后未做 r=0 / r+k=n 检查的边界条件 |
| 私钥泄露类安全事件 | k 重用或随机数质量；改用设备内签名或确定性签名 |
| 压缩公钥兼容问题 | 证书/协议栈普遍只接受 04 未压缩格式 |
